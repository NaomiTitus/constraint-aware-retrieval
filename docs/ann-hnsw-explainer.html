The problem ANN solves

Exact nearest-neighbour search is a loop. Take the query vector, compute a distance against every vector in the corpus, keep the best k. It is O(N·d), embarrassingly parallel, and completely exact.

At our scale that is not a problem worth solving:

Approximate nearest neighbour search gives up certainty to buy time. It returns vectors that are probably the closest. The quality of that "probably" is measured as recall@k — of the true k nearest, how many did the index actually return — and it is a tunable, not a fixed property.

That framing matters: ANN is not a faster exact algorithm. It is a different answer to a slightly different question, and whether the difference costs you anything is an empirical question about your data and your k.

HNSW: a skip list for metric space

Hierarchical Navigable Small World is the index Qdrant, FAISS, Weaviate and pgvector all default to. It builds a layered proximity graph:

  • Layer 0 holds every vector, linked to its close neighbours.
  • Each layer above holds an exponentially thinning random sample, with edges spanning much longer distances.

Search enters at the single top node and walks greedily downhill toward the query. When no neighbour in the current layer is closer, it drops a layer and continues on a finer mesh. Top layers cover ground fast; lower layers refine. Roughly O(log N) hops instead of N comparisons.

Filtering breaks the walk

Now add a constraint. In this project the decisive one is "don't show me ads that require Norwegian" — and only around 5% of the corpus qualifies as English-accessible. That is a highly selective filter, and it is where naive approaches fall apart.

HNSW's navigability is a property of the whole graph. Delete most of the nodes and the survivors may not be connected to each other at all: a greedy walk that can only step on valid nodes gets marooned in whatever region it started in, and never reaches equally-good matches elsewhere.

Pre-filter Compute the matching subset first, then brute-force within it. The subset is still large — you're back to O(N·d). exact & fast
In-engine Traverse the full graph for connectivity, but only collect passing nodes. Rarely — but it costs extra hops through rejected nodes. good recall
Note the inversion. Pre-filtering is the best option at high selectivity and the worst at low selectivity; post-filtering is the reverse. There is no single right answer — which is exactly why it is worth measuring rather than assuming.

What Qdrant actually does

Qdrant stores a JSON payload beside every vector and indexes the fields you nominate. A query carries both a vector and a filter, and the engine decides how to execute the pair:

  1. Estimate the filter's cardinality from the payload index — roughly how many points will pass.
  2. If few points pass, skip the graph entirely and brute-force the matching subset. Exact, and fast because the subset is small.
  3. If many points pass, traverse HNSW normally and apply the filter as a predicate during traversal — walking through rejected nodes to stay connected, but only admitting passing ones into the result heap.
  4. For filters used constantly, build additional graph links restricted to that subset, restoring navigability within it.

That cardinality-driven switch is the real feature, and it is why "just use FAISS plus a mask" is not equivalent. FAISS has no payload concept; you would be hand-rolling steps 1–4.

Why this is worth an experiment rather than a paragraph. Our constraint sits right at the awkward end of the range — selective enough that post-filtering should fail, large enough (≈500 ads) that brute force is trivially affordable. Measuring recall@10 and latency across all three strategies, on our real skew, produces a defensible answer to "when should a marketplace adopt filtered vector search?" — and at 10k vectors the honest answer may well be "not yet", which is a finding, not a failure.
